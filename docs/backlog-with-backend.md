# 서버와 함께 처리할 백로그

API 서버(WaggleAPIServer)와 웹을 함께 바꿔야 하는 항목을 모은 문서다. 웹만으로 고칠 수 있는 항목은 [프론트엔드 개선 백로그](backlog.md)에 있다.

- 기준 커밋: 웹 `dee2918` (`main`, PR #269 머지 시점), 서버 `1d74adb` (multi-device-refresh 반영 시점)
- 이 문서의 항목은 웹 혼자 시작하지 말 것. 서버 개발자와 API 계약과 배포 순서를 먼저 정한 뒤 진행한다
- 항목마다 **주도**를 적었다
  - 서버 주도: 서버가 계획했거나 진행 중인 변경이고, 웹이 따라가야 함
  - 웹 요청: 웹의 문제를 풀려면 서버가 바뀌어야 함
- 항목마다 **배포** 칸에 순서를 적었다
  - 동시 배포: API 계약이 바뀌어 서버와 웹을 함께 배포해야 함
  - 서버 선행: 서버를 먼저 배포하고, 웹은 그 뒤에 바꿈
  - 웹 선행: 웹을 먼저 바꿔 두면 서버를 언제 배포해도 문제가 없음
  - 정책에 따라: 해결 방식을 정한 뒤에 결정
- **정할 것**은 서버와 웹 개발자가 API 계약이나 배포 순서를 함께 정해야 하는 것이다
- 요약 표의 **서버** 열은 WaggleAPIServer `docs/backlog.md`의 대응 항목 ID다. 서버 문서가 없어도 각 항목의 **서버 계획**만 읽으면 웹이 할 일을 알 수 있게 적었다
- 일부 항목은 **노션 화면설계서**를 근거로 든다. 기획이 관리하는 노션 문서(WAGGLE 0.3 NOTE)로, 화면마다 ID를 붙여 정책을 적어 둔다. 이 문서에 나오는 ID는 RC-02(모집글 상세), RC-04(모집글 수정), TM-04(팀 관리), TM-07(모집글 관리)이다. 근거가 되는 문장은 항목 안에 인용했으므로 노션에 들어가지 않아도 된다
- 우선순위 기준(P0~P3, 서비스 흐름의 중요도)은 [프론트엔드 개선 백로그](backlog.md)와 같다
- 항목을 처리하면 그 PR에서 이 문서의 해당 항목을 지울 것

## 서버 오류 응답 형식

웹 코드에는 서버 오류 응답 타입이 없다. 여러 항목이 "서버가 정한 오류 코드일 때"를 기준으로 분기하므로, 서버 코드에서 확인한 형식을 여기 적는다.

- **REST**: 오류 응답 본문은 `{ status: number, code: string, message: string, detail?: string }`이다. `code`는 서버 `ErrorCode` enum의 이름이다
  - `INVALID_INPUT_VALUE`, `INVALID_TYPE_VALUE`, `INVALID_STATE` (400)
  - `INVALID_TOKEN`, `UNAUTHORIZED`, `OAUTH_EMAIL_NOT_VERIFIED`, `OAUTH_EMAIL_MISSING`, `OAUTH_OTT_INVALID` (401)
  - `ACCESS_DENIED` (403), `ENTITY_NOT_FOUND` (404), `DUPLICATE_RESOURCE` (409), `INTERNAL_SERVER_ERROR` (500)
- **STOMP**: 메시지 처리에 실패하면 보낸 사람의 `/user/queue/errors`로 같은 모양의 객체를 보낸다
  - 레이트 리밋 초과: `status: 429`, `code: "TOO_MANY_REQUESTS"`
  - 내용 검증 실패: `code: "INVALID_INPUT_VALUE"`, `detail`에 필드별 사유
  - 그 밖의 실패(자기 자신에게 보내기, 탈퇴한 수신자 등): 위 REST 목록의 `code`
- 아래 항목에서 "오류 코드는 서버를 구현할 때 정한다"고 적은 곳은 새 `ErrorCode`가 생기거나 기존 코드(주로 `INVALID_STATE`)를 쓰게 된다. 서버 개발자에게 이름을 받아 분기한다

## P1

### S1. 모든 커서 기반 API의 커서를 인코딩된 문자열로 통일

- **주도**: 웹 요청 (서버 M1)
- **웹이 원하는 것**: 서버 공통 모듈에서 커서를 인코딩한 불투명 문자열로 바꾸고, 정렬 값이 하나뿐인 커서까지 모든 커서 기반 API에 적용한다. 그러면 웹은 커서 값의 내용을 해석하지 않고, 받은 `nextCursor`를 다음 요청에 그대로 돌려주기만 하면 된다. 서버는 정렬 값이 ID가 아닌 목록의 결함만 확인했고, 모든 커서를 통일할지는 정하지 않았다.
- **왜 바꾸는가**: 지금은 커서가 마지막 항목의 ID 하나다. 조회순이나 좋아요순처럼 ID가 아닌 값으로 정렬하면, 서버가 매 요청마다 커서 항목의 현재 값을 다시 읽는다. 그래서 그 항목이 삭제되거나 값이 바뀌면 목록이 끊기거나 중복된다. 지원자 관리 목록도 같은 문제가 있다. 매니저가 1페이지 마지막 지원서를 승인하면 다음 페이지가 남은 대기 지원서를 건너뛴다. 웹은 지금 지원자 목록의 2페이지를 부르지 않아 드러나지 않을 뿐인데, 이를 고치면([프론트엔드 개선 백로그](backlog.md) P0-2) 바로 드러난다. 커서에 정렬 값을 함께 담으면 이 문제가 없어진다.
- **웹에서 바꿀 곳**
  - 타입: `nextCursor: number | null` (`types/api/posts.ts:86`, `message.ts:32`, `user.ts:33`, `team.ts:53, 94`), 요청 파라미터 `cursor?: number` (`types/api/posts.ts:96`, `team.ts:101`, `api/message.ts:10, 21`)를 `string`으로 바꾼다
  - 캐스팅: `pageParam as number` (`hooks/useMessage.ts:16, 35, 52`), `initialPageParam: undefined as number | undefined` (`useMessage.ts`, `usePost.ts:145`, `useTeam.ts:106`)
  - **타입만 바꾸면 놓치는 곳**: `hooks/usePost.ts:147, 164`와 `api/post.ts:55`는 `typeof cursor === 'number'`가 아니면 커서를 버린다. 문자열 커서가 오면 오류 없이 `hasNextPage`가 false가 되어, 홈 화면 무한 스크롤이 첫 페이지에서 멈춘다. 이 검사들을 지워야 한다
- **서버에 요청할 것**
  - **메시지 하이라이트 이동용 기준점 파라미터**: 메시지 검색 결과에서 해당 메시지로 이동하는 기능(`hooks/useChatLogic.ts:61-83`)은 메시지 ID를 커서로 쓴다. 그 메시지 ID + 1부터 과거 방향(`BEFORE`)으로, 그 ID부터 최신 방향(`AFTER`)으로 조회한다. 커서가 불투명해지면 이 방식을 쓸 수 없다. 그래서 `aroundMessageId` 같은 별도 파라미터가 필요하다. 응답으로는 그 메시지를 포함한 첫 페이지와 양방향 커서를 받는다
  - **커서와 조회 조건의 일치 검증**: 커서에 정렬 기준과 필터도 함께 담는다. 다른 조건으로 만든 커서가 오면 400으로 거부한다
- **웹에서 추가로 할 일**
  - 커서 오류(400)를 받으면 그 목록을 첫 페이지부터 다시 불러온다
  - 배포 전에 저장된 쿼리 캐시에는 숫자 커서가 남아 있다. 배포 직후 그 캐시로 다음 페이지를 요청하면 커서 오류가 난다. 캐시 버전(`buster`)을 같은 배포에 넣는다([프론트엔드 개선 백로그](backlog.md) P0-3)
- **정할 것**: 커서 오류(다른 조건으로 만든 커서)의 `code`, 모든 커서를 통일할지와 그 범위, 메시지 기준점 파라미터와 커서 검증을 둘지, 서버와 웹을 같은 시점에 배포할지 또는 서버가 일정 기간 숫자 커서와 문자열 커서를 둘 다 받을지
- **배포**: 동시 배포

### S2. 팀 상태 전이와 완료 처리를 서버 한 곳에서 처리

- **주도**: 웹 요청 (서버 M8)
- **지금의 동작**
  - 웹: 모집글을 처음 만들 때 팀이 PREPARING이면, 웹이 따로 `{ status: 'ACTIVE' }` 요청을 보내고 결과를 기다리지 않은 채 이동한다(`hooks/usePost.ts:171-186`). 실패해도 처리하지 않는다
  - 웹: 팀 완료는 웹이 모집글 N개를 `Promise.all`로 마감한 뒤 팀 상태를 바꾼다(`pages/TeamStatusPage.tsx:280-319`). 마지막 요청이 실패하면 모집글은 모두 닫혔는데 팀은 ACTIVE로 남는다
  - 서버: 같은 상태로 바꾸는 것만 막는다. 그래서 완료와 진행 중을 자유롭게 오갈 수 있고, 완료로 바꿀 때마다 전 멤버에게 리뷰 요청 알림이 다시 간다. 완료된 팀에도 지원과 승인이 들어온다
- **영향**: 팀 상태와 모집글 상태가 어긋난다. 완료된 팀에 지원이 쌓인다. 완료 후 승인된 사람도 바로 다른 멤버를 리뷰할 수 있어서, 협업 온도의 신뢰도가 떨어진다.
- **서버에 요청할 것**
  - 모집글을 처음 만들면, 서버가 같은 트랜잭션에서 팀을 ACTIVE로 바꾼다
  - 팀을 완료하면, 서버가 열린 모집을 함께 닫는다
- **정해진 것**: 팀 완료는 되돌릴 수 없는 최종 상태다. 노션의 완료 확인 모달 문구가 "'완료' 후에는 팀원 모집과 공고가 마감되며, 이전 상태로 되돌릴 수 없습니다."이고, TM-04도 완료 상태에서 "모집하기"를 비활성화한다
  - 웹은 이미 이 정책대로 동작한다. `TeamStatusPage`의 상태 카드는 완료 상태에서 팀 화면으로 이동할 뿐 상태를 되돌리지 않는다
  - 서버는 이 정책을 강제하지 않는다. 그래서 서버 계획은 완료를 최종 상태로 막고, 완료된 팀의 지원, 승인, 모집글 수정을 거부하고, 리뷰 요청 알림은 처음 완료될 때만 보내는 것이다
- **웹에서 바꿀 곳**
  - 서버가 바뀐 뒤 상태 변경 요청을 하나로 줄이고, `team-detail`, `user-me-team` 캐시를 무효화한다. 줄일 곳은 `hooks/usePost.ts:171-186`(첫 모집글 뒤 진행 중 전환)과 `pages/TeamStatusPage.tsx:280-319`(완료 전 모집글 마감)이다. 같은 완료 버튼의 중복 제출 방지는 [프론트엔드 개선 백로그](backlog.md) P1-3에 있다
  - 서버가 완료된 팀의 지원, 승인, 모집글 수정을 거부하게 되면, 그 요청의 실패 안내를 띄운다. 서버 백로그의 권장안은 `INVALID_STATE`(400)다. 이 코드는 다른 거부에도 쓰이므로 요청마다 안내 문구를 따로 둔다
- **확인**: 코드 추적 (웹과 서버 양쪽)
- **배포**: 서버 선행

### S3. 팀을 떠난 작성자와 남은 팀원 사이에서 모집글 수정, 삭제 권한이 어긋남

- **주도**: 서버 주도 (서버 H5)
- **지금의 동작**
  - 서버: 모집글 삭제는 작성자 본인인지만 보고, 지금 팀 멤버인지는 보지 않는다. 수정은 작성자인지 확인한 뒤 멤버인지 보지만, 역할은 보지 않는다. 모집글 생성과 마감은 "현재 팀 매니저 이상"을 요구한다
  - 웹: 작성자 본인에게만 수정, 삭제 버튼을 보여 준다(`pages/PostDetailPage.tsx:150`의 `isMyPost`). 수정 화면 진입은 역할로 막는다(`loaders/routeLoaders.ts`의 `postEditLoader`). 그래서 작성자라도 지금 역할이 일반 멤버면 버튼은 보이지만 수정 화면에 들어갈 수 없다
- **결함인 부분**
  - 팀에서 추방된 매니저도 그 팀의 모집글을 지울 수 있다. 지원서, 댓글, 알림까지 함께 지워진다
  - 작성자가 팀을 떠나면 그 글은 누구도 수정하거나 삭제할 수 없다
- **근거 문서**: 노션 RC-04(모집글 수정)는 수정 화면 진입 조건을 "작성자(또는 팀장/관리자 권한 보유)"로, RC-02(모집글 상세)는 삭제할 수 있는 사람을 "작성자 본인 한 명"으로 적어 문서끼리 다르다. 팀장은 `LEADER`, 관리자는 `MANAGER` 역할이다
- **서버 계획**: 수정과 삭제 모두 RC-04 기준으로 맞춘다. 작성자이면서 지금 그 팀의 멤버이거나, 작성자가 아니어도 지금 팀에서 `MANAGER` 이상(`LEADER`, `MANAGER`)이면 수정, 삭제할 수 있다. 팀을 떠난 작성자는 수정, 삭제할 수 없다
- **웹에서 바꿀 곳**
  - 수정, 삭제 버튼 노출 조건을 `isMyPost`(`pages/PostDetailPage.tsx:150`)에서 위 기준으로 바꾼다
  - 조회한 사용자의 팀 역할은 서버 상세 응답의 `team.memberRole`(`LEADER`, `MANAGER`, `MEMBER`)에 있고, 팀 멤버가 아니면 필드가 빠진다. 그런데 웹 타입 `TeamResponse`(`types/api/team.ts:3-16`)는 이 필드 대신 `role`을 필수로 선언한다. `role`은 내 팀 목록 응답에 있는 필드라, 상세 응답에서는 늘 `undefined`다. 상세용 팀 타입에 `memberRole?: 'LEADER' | 'MANAGER' | 'MEMBER'`를 추가해 그 값으로 판정한다 버튼 노출 조건과 `postEditLoader`의 진입 조건은 같은 함수 하나로 판정해 서로 어긋나지 않게 한다.
- **배포**: 서버 선행. 웹이 먼저 바뀌면 서버가 거부할 버튼이 보인다

### S13. 지원자가 있는 모집글의 삭제를 막음

- **주도**: 서버 주도 (서버 M14)
- **지금의 동작**
  - 서버: 모집글 삭제는 작성자인지만 확인하고, 지원서가 있는지는 보지 않는다. 삭제하면 그 글의 지원서도 함께 soft delete되어, 지원자의 지원 내역이 알림 없이 사라진다
  - 웹: 지원자가 있어도 삭제 버튼이 활성화되어 있다. 모집글 관리 탭의 "모집 글 삭제" 버튼(`components/Team/TeamPostItem.tsx:138-145`)은 확인 없이 바로 삭제 요청을 보낸다. 모집글 상세의 삭제 아이콘(`pages/PostDetailPage.tsx:299`)은 확인 모달을 거쳐 `deletePostMutate`(`:564`)를 부른다
- **근거 문서**: 노션 RC-02(모집글 상세)와 TM-07(모집글 관리)은 지원자가 있는 모집글을 삭제할 수 없다고 정했다. TM-07은 지원자가 0명일 때만 삭제할 수 있고, 목록에 지원자 수를 함께 보여 준다
- **서버 계획**: 삭제되지 않은 지원서(대기 `PENDING`, 승인 `APPROVED`, 거절 `REJECTED`)가 하나라도 있으면 삭제를 거부한다. 지원자가 취소한 지원서는 soft delete되므로 세지 않는다. 서버 백로그의 권장안은 `INVALID_STATE`(400)로 거부하는 것이다. 이 코드는 다른 거부에도 쓰이므로, 삭제 요청의 실패로 이 코드가 오면 지원자가 있어 삭제할 수 없다고 안내한다
- **지원자 수를 얻는 곳**
  - 팀 모집글 목록 응답(`GET /teams/{teamId}/posts`)의 `applicantCount`는 서버가 삭제되지 않은 지원서를 상태와 상관없이 센 값이라, 서버의 삭제 거부 기준과 같다. `TeamPostItem`이 prop으로 받아 `{applicantCount}명`으로 그린다(`TeamPostItem.tsx:109`)
  - 모집글 상세 응답에는 지원자 수가 없다. 웹은 팀 모집글 목록 타입을 상세 타입으로 재사용한다(`GetTeamPostsResponse = PostDetailResponse[]`, `types/api/posts.ts:112`). 그래서 `PostDetailResponse.applicantCount`(`:80`)는 목록에서는 값이 오고, 상세에서는 늘 `undefined`다
- **서버에 요청할 것**: 모집글 상세 응답에 지원자 수를 추가할지. 추가하지 않으면 상세 화면은 버튼을 미리 막지 못하고, 서버 거부 응답으로만 알린다
- **웹에서 바꿀 곳**
  - 모집글 관리 탭: `applicantCount > 0`이면 "모집 글 삭제" 버튼을 비활성화하고, 지원자가 있어 삭제할 수 없다는 안내를 보여 준다. 안내 문구는 웹이 정한다
  - 모집글 상세: 서버가 지원자 수를 주면 같은 방식으로 막는다. 주지 않으면 삭제 요청의 `onError`(`PostDetailPage.tsx:564` 아래, 지금은 "모집글 삭제 중 오류가 발생했습니다." 하나뿐)에서 서버가 정한 오류 코드일 때 같은 안내를 띄운다
  - 서버가 상세 응답에 필드를 추가하지 않으면, 팀 모집글 목록용 타입을 따로 만들어 `applicantCount`를 그쪽으로 옮긴다. 선언만 지우면 `TeamPostItem`이 컴파일되지 않는다
  - 모집글 관리 탭 버튼의 확인 단계는 [프론트엔드 개선 백로그](backlog.md) P1-3에 있다. 같은 버튼이므로 함께 고친다
  - 버튼을 막아도 화면을 연 뒤에 지원이 들어오면 서버가 거부한다. 모집글 관리 탭도 같은 오류 코드를 처리한다
- **확인**: 코드 추적 (웹과 서버 양쪽)
- **배포**: 웹 선행. 모집글 관리 탭의 버튼은 먼저 막아 둘 수 있다. 서버 거부 오류의 처리는 서버가 오류 코드를 정한 뒤에 넣고, 상세 응답에 지원자 수를 추가하면 그 부분은 서버 선행이다

### S4. 메시지 전송 결과를 어느 메시지의 결과인지 알 수 있게 돌려주기

- **주도**: 웹 요청 (서버 백로그에 아직 없음)
- **지금의 동작**
  - 서버는 전송에 실패하면 보낸 사람의 `/user/queue/errors`로 오류를 보낸다. 하지만 오류에 어느 메시지의 실패인지 알려 주는 식별자가 없다
  - 전송에 성공해도 보낸 사람에게는 아무것도 돌려주지 않는다. 받는 사람에게만 메시지를 보낸다
  - 그래서 웹은 800ms 뒤 히스토리를 다시 조회하고, "내용, 발신자, 30초 이내"가 같은 메시지를 찾아 임시 메시지를 확정한다(`hooks/useChatLogic.ts:13, 99-117, 385-388`)
- **영향**: 서버 저장이 800ms보다 늦으면 임시 메시지가 계속 남는다. 같은 내용("ㅇㅇ")을 연달아 보내면 짝이 잘못 맞는다.
- **서버에 요청할 것**: 전송 요청에 웹이 만든 `clientMessageId`(UUID)를 받는다. 성공하면 저장된 메시지를, 실패하면 오류를 그 ID와 함께 보낸 사람에게 돌려준다.
- **정할 것**: 성공 응답을 보낼 destination(기존 `/user/queue/messages`를 함께 쓸지, 새 큐를 둘지), 메시지와 오류 페이로드에서 `clientMessageId`를 실을 필드 이름
- **웹에서 바꿀 곳**: 돌아온 `clientMessageId`로 임시 메시지를 확정하거나 실패로 표시한다. 800ms 타이머와 내용 비교 로직은 지운다. 오류 채널 구독은 서버 변경과 상관없이 먼저 한다([프론트엔드 개선 백로그](backlog.md) P1-4).
- **확인**: 코드 추적 (서버의 메시지 전달과 오류 처리 확인)
- **배포**: 동시 배포

### S6. 응답 enum에 값을 추가할 때의 배포 순서

- **주도**: 웹 요청 (서버 백로그에 아직 없음)
- **배경**: 지금 웹은 모르는 알림 타입을 받으면 렌더 중 예외가 나고, 화면 전체가 404로 바뀐다([프론트엔드 개선 백로그](backlog.md) P0-1). 웹에서도 고칠 예정이지만, 고친 뒤에도 새 타입은 기본 모양으로만 보인다.
- **정할 것**: 서버가 응답 enum에 값을 추가할 때는 웹을 먼저 배포한다는 순서 규칙. 대상은 알림 타입, 지원 상태, 팀 상태, 포지션, 스킬 등이다
- **끝나는 조건**: 웹이 할 코드 작업은 없다. 서버 개발자와 규칙을 합의해 두 저장소의 기여 문서(서버 `CLAUDE.md`, 웹 README 등)에 적으면 이 항목을 지운다
- **배포**: 정책에 따라

### S14. 팀을 삭제해도 알림과 지원 이력이 남게 됨

- **주도**: 서버 주도 (서버 M16)
- **지금의 동작** (서버): 팀장이 팀을 지우면 그 팀의 멤버십, 지원서, 지원서 열람 기록을 soft delete하고, 그 팀과 팀 모집글에 걸린 알림을 지운다. 팀 삭제를 알리는 알림은 없다. 리뷰와 협업 온도는 남는다. 멤버십이 지워지므로 그 팀은 팀원들의 프로필 팀 목록에서도 사라진다
- **근거 문서**: 노션 TM-04(팀 관리)의 팀 삭제 범위
  - 검토 중인 지원서는 자동으로 종료하고, 지원자에게 알린다. 화면 표기는 제안값으로 "모집 종료"가 적혀 있다
  - 처리된 지원 이력(승인, 거절)은 남긴다
  - 리뷰와 협업 온도는 남긴다
  - 받은 알림은 남긴다. 삭제된 팀의 알림을 누르면 "삭제된 팀이에요" 토스트를 띄운다
  - 팀원에게 팀이 삭제됐다고 알린다
  - 완료된 팀은 이력에서 "삭제된 팀"으로 표시한다
- **서버 계획**: 위 범위대로 바꾼다. 팀 삭제 알림 타입을 새로 추가한다(이름은 서버가 정함. 예: `TEAM_DELETED`). 검토 중 지원서의 종료를 새 지원 상태로 둘지(지금 지원 상태는 `PENDING`, `APPROVED`, `REJECTED` 셋), 기존 상태로 처리할지도 서버가 정한다
- **웹에서 바꿀 곳**
  - **새 알림 타입**: 알림 화면은 타입별 설정 객체(`components/Notifications/index.tsx`의 `NOTIFICATION_CONFIG`)에서 아이콘, 문구, 이동 경로를 꺼낸다. 모르는 타입을 받으면 렌더 중 예외로 화면 전체가 404가 되므로([프론트엔드 개선 백로그](backlog.md) P0-1), 새 타입의 설정을 서버 배포 전에 추가한다(S6). 알림 문구와 아이콘은 다른 타입처럼 웹이 정한다. 새 지원 상태가 생기면 상태를 따로 선언하거나 세는 곳을 모두 바꾼다: `types/api/user.ts:4`(`ApplicationStatus`), `:39-40`(화면 표기 `ApplicationStatusLabel`), `types/api/posts.ts:79`(`PostDetailResponse.applicationStatus`), `types/api/team.ts:35`(`ApplicantResponse.status`), `components/Profile/ProfileApplicationSection.tsx:34`(상태별 집계)
  - **팀 정보가 빠진 알림**: 서버는 알림을 만들 때 찾지 못한 팀과 모집글을 `metadata`에서 뺀다. 지금 `NOTIFICATION_CONFIG`의 문구와 경로는 `metadata.team`이 항상 있다고 가정하므로, 알림을 남기기 시작하면 이 경우를 먼저 처리한다
  - **삭제된 팀의 알림 클릭**: 지금은 알림을 누르면 읽음 처리 뒤 `getRoute`의 경로(대부분 `/team/{teamId}`)로 이동한다(`components/Notifications/index.tsx:163-169`). 삭제된 팀이면 그 화면이 404가 되므로, 이동하지 않고 "삭제된 팀이에요" 토스트를 띄운다
  - **완료된 팀 이력**: 프로필의 팀 목록(`components/Profile/ProfileTeamSection.tsx`의 `MyPageCard`)에서 삭제된 완료 팀을 "삭제된 팀"으로 표시한다. 서버가 삭제된 팀도 이 목록에 내려 주도록 바뀐 뒤의 일이다. TM-04는 완료된 팀만 이력에 남긴다고 적었으므로, 완료 전에 삭제된 팀은 지금처럼 목록에서 빠지는 것으로 본다
- **정할 것**: 팀 삭제 알림 타입의 이름과 `metadata` 모양, 검토 중 지원서의 종료 상태 값, 삭제된 팀을 응답에서 어떻게 나타낼지. 알림 `metadata.team`, 프로필 팀 목록의 팀에 삭제 여부 필드(예: `deleted: true`)를 둘지, 팀을 `null`로 줄지. 웹이 위 세 가지를 판정하는 기준이 된다
- **확인**: 서버 코드 추적, 노션 TM-04 대조. 웹은 알림 클릭 경로와 프로필 팀 목록 컴포넌트까지만 확인했고, 삭제된 팀이 들어왔을 때의 동작은 재현하지 않았다
- **배포**: 웹 선행. 위의 정할 것을 서버와 먼저 합의하고, 그 계약대로 웹이 새 알림 타입과 삭제된 팀 표시를 먼저 배포한 뒤 서버를 배포한다

### S10. 약관 미동의 응답이 400에서 전용 403으로 바뀜

- **주도**: 서버 주도 (서버 L1, 보류 중)
- **서버 계획**: 필수 약관에 동의하지 않은 사용자의 요청은 지금 400(`INVALID_STATE`)으로 거부된다. 일반 유효성 오류와 코드가 같아 구분할 수 없다. 약관이 개정되면 서버는 바뀐 약관의 새 버전에만 다시 동의를 받는다. 이 흐름은 이미 있다. 남은 것은 전용 오류 코드와 403으로 바꾸는 일이다.
- **웹에서 바꿀 곳**: 지금 웹은 `GET /terms`로 동의 여부를 미리 확인해 약관 모달을 띄우므로, 이 응답에 의존하지 않는다. 다만 `pages/RouteErrorPage.tsx`는 403이면 "권한 없음" 페이지를 보여 준다. 그래서 서버가 바꾸면 전용 오류 코드일 때 약관 모달로 보내는 분기가 필요하다. 코드 이름은 서버를 구현할 때 정한다. `TermsModal`은 지금 `MainPage`에서만 뜨므로, 분기를 axios 응답 인터셉터(`api/axiosInstance.ts`)나 `RouteErrorPage`에 두고 어느 화면에서든 모달을 열 수 있게 한다.
- **배포**: 웹 선행. 코드 이름을 받은 뒤 분기를 먼저 넣어 두면, 서버가 언제 바꿔도 "권한 없음" 화면이 잘못 뜨지 않는다

### S11. 마케팅 수신 동의를 철회하는 화면

- **주도**: 서버 주도 (서버 L14)
- **서버 계획**: 지금 서버는 선택 약관(마케팅)의 동의만 저장하고, 미동의는 무시한다. 서버는 철회를 기록하도록 고칠 계획이다.
- **웹에서 바꿀 곳**: 웹은 해제한 약관을 `agreed: false`로 보내므로 요청 형식은 바꿀 필요가 없다. 하지만 동의한 뒤 철회할 화면이 없다. `TermsModal`은 필수 약관에 동의하지 않았을 때만 뜬다. 마이페이지 등에 동의 상태를 보고 바꾸는 화면이 필요하다. 화면 위치와 디자인은 정해지지 않았으므로 기획, 디자인 담당과 정한 뒤 시작한다.
- **주의**: 마케팅 발송을 붙이기 전에 반드시 처리할 것. 철회할 방법이 없으면 정보통신망법의 수신 동의 철회 요건과 충돌할 수 있다
- **배포**: 서버 선행

### S12. 이미지 업로드 방식이 presigned PUT에서 presigned POST로 바뀔 수 있음

- **주도**: 서버 주도 (서버 M11, 검토 중)
- **지금의 방식**: 서버는 S3 presigned **PUT** URL을 발급하고, 웹은 그 URL에 파일 본문을 `PUT`으로 올린다. presigned PUT은 업로드 경로와 Content-Type은 서명으로 고정할 수 있지만, 파일 크기는 제한할 수 없다. 그래서 지금은 URL만 받으면 최대 5GB까지 올릴 수 있다.
- **서버 계획**: S3는 presigned **POST**라는 별도 방식을 제공한다. 서버가 업로드 조건(정책)에 서명해 URL과 폼 필드를 함께 주고, 클라이언트는 그 필드와 파일을 `multipart/form-data`로 `POST`한다. 이 정책에는 `content-length-range`로 크기 범위를 넣을 수 있다. 서버는 크기 제한을 위해 이 방식으로 바꿀지 검토하고 있다. 버킷 수명 주기 규칙만 두고 지금 방식을 유지하는 방안도 있다. 크기 상한은 서버가 정해 근거와 함께 기획에 알린다. 상한이 정해지면 웹도 업로드 전에 같은 상한을 검사한다.
- **웹에서 바꿀 곳**: presigned POST로 바뀌면 응답 형식이 URL 하나에서 URL과 폼 필드로 바뀐다. 그래서 웹의 업로드 3곳(`hooks/useUser.ts`, `pages/TeamFormPage.tsx`, `components/Field/FieldBody.tsx`)을 `PUT` 본문 업로드에서 `FormData` `POST`로 바꿔야 한다. 공통 업로드 함수로 먼저 모아 두면 한 곳만 바꾸면 된다([프론트엔드 개선 백로그](backlog.md) P3-4).
- **배포**: 정책에 따라. 수명 주기 규칙만 두면 웹 변경은 없다
